> **한 문장 요약**: OpenAI가 GPT-6 Astra의 제한적 배포를 시작하고 비동기 도구 호출, 작업 중 지시 변경과 안전 감시를 에이전트 실행 흐름에 결합했다.

## 무엇이 발표됐나

OpenAI는 9월 3일 GPT-6 Astra를 일부 조직부터 배포하고 이후 수일에 걸쳐 접근을 확대한다고 밝혔다. 출시일에 모든 계정이 사용할 수 있었다는 뜻은 아니다. API 식별자는 `gpt-6-astra`이며 표준 입력·출력 가격은 100만 토큰당 10달러·50달러다. 개발자에게 중요한 변화는 코딩·컴퓨터 사용 성능뿐 아니라 긴 작업에 지시와 도구 결과를 투입하는 실행 방식이다.

## 도구를 기다리는 동안에도 작업은 진행된다

공식 개발자 가이드에 따르면 함수·커스텀 도구에 `async: true`를 설정하면 모델이 독립적인 추론이나 다른 도구 호출을 계속할 수 있다. 애플리케이션은 도구를 직접 실행하고 원래 `call_id`로 결과를 돌려준다. WebSocket의 작업 중 지시 변경은 완료한 작업을 보존한 채 새 요구를 후속 실행에 반영한다. 이는 [초기 Responses API의 도구 루프](/posts/2025-03-openai-responses-agents-sdk)에 진행 중 작업 관리가 더해진 형태다.

내 판단으로는 실행기가 작업별 상태와 지시 버전을 명시적으로 가져야 한다. 사용자가 범위를 줄인 뒤 예전 지시로 시작한 검색 결과가 도착하면, 이를 계속 사용할지 폐기할지 결정해야 한다. 취소된 작업의 늦은 응답, 중복 전달, 도구 타임아웃도 정상적인 상태 전이로 처리할 필요가 있다. 모델이 병렬로 진행할 수 있다는 사실이 쓰기 작업의 순서와 멱등성을 보장하지는 않는다.

## 비동기 안전 감시의 중단 경계

Misalignment monitoring은 모델의 추론과 행동을 비동기로 검사한다. Responses API에서 추론 상태 보존, WebSocket 또는 OpenAI compaction을 쓰는 요청은 자동 중단이 가능하다. 이 방식을 쓰지 않는 Responses 요청도 감시하지만 자동 중단은 하지 않으며, Chat Completions는 이 감시 체계의 적용 대상이 아니다.

차단 오류 `misalignment_policy_violation`을 받으면 해당 대화의 추가 실행을 멈추고 자동 재시도하지 않아야 한다. 감시가 늦게 도착할 수 있어 이미 완료한 쓰기는 되돌려지지 않는다. 경보 수신과 실제 취소를 별개로 추적하고, [샌드박스의 권한 경계](/posts/2026-05-codex-windows-sandbox)와 애플리케이션의 승인·복구 절차를 유지해야 하는 이유다.

## 한계와 검증 포인트

OpenAI는 OSWorld 2.0 지연 시뮬레이션에서 72.6%와 작업당 약 40분을 보고했다. 이는 오프라인 부분집합의 부분점수이며 모든 업무의 완료율이나 실측 지연으로 일반화할 수 없다. 도구 호출은 Responses API가 필요하고 `none` 추론 노력, 사용자 지정 `temperature`·`top_p` 등은 지원하지 않아 기존 클라이언트의 호환성도 확인해야 한다.

도입 평가는 작업 성공률·총비용·사람 개입 시간에 더해 지시 변경 후 잘못된 실행과 중단 뒤 추가 쓰기 발생을 측정하는 것이 좋다. 안전 경보의 오탐과 누락도 측정 대상이다. 이 글은 AI로 공식 자료를 조사·구조화했으며 모델 벤치마크나 API 동작을 직접 재현하지 않았다.
